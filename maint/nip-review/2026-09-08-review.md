# Review of the September NIP update

Reviewed PR #3 at `2f66d7f`, then added regression tests and corrections on the
same branch. The original green CI result did not establish complete edge-case
coverage: this review found functional bugs and documentation gaps.

The review compared changed requirements at NIPs commit `c3fd9af1` with the
implementation, conformance tests, public entry points, and POD. Sources were
NIP-01 subscriptions/limits, NIP-22 comments, NIP-29 group references, metadata,
moderation, membership, subgroups and migration, NIP-34 pull requests, NIP-42
AUTH ordering, NIP-46 unsupported methods, NIP-47 Info Event/Encryption,
NIP-51 lists, NIP-67 hints, NIP-78 AUTH, and NIP-A3 target tags/rendering.

## Findings corrected

| Finding | Correction and evidence |
| --- | --- |
| Rapid joins/leaves could reuse generated event IDs, and creation produced no kind-9000 membership record. The most recent membership event could disagree with current state. | RelayGroups emits a relay-signed membership transition for creation and every accepted membership action. Timestamps advance beyond the triggering request and all earlier transitions for that group/member. Wire tests cover creation, repeated joins/leaves, explicit add/remove operations, future-dated requests, and reconstruction from the newest record. |
| Group metadata validation checked the new parent/banner fields but accepted malformed legacy fields, conflicting flags and invalid supported kinds. The edit builder could not express supported kinds. | Shared structural validation covers all recognized metadata fields, empty/duplicate group tags, kind boundaries and contradictory edit flags. The builder supports supported kinds and LiveKit metadata; the optional relay policy still rejects AV service edits. Rejection tests verify storage remains unchanged. |
| Pin parsing and other moderation builders did not consistently validate timeline references; group references accepted empty IDs and ignored unknown builder options. | Validate timeline shapes and eight-character lowercase hex prefixes, reject empty decoded/built group IDs, and reject unknown reference options. Includes the NIP-29 timeline example. |
| An explicit empty encryption advertisement silently became legacy NIP-04. | Preserve the empty tag and empty scheme list. Only an absent tag implies NIP-04. Constructor/parser round-trip regression covers the distinction. |
| An unrelated raw group ID beginning with `naddr1` could reject an entire valid discovery list or migration. | Interpret a value as a metadata reference only when it decodes successfully; otherwise retain it as an arbitrary raw ID. Exact configured raw IDs take precedence. Tests cover both discovery and migration without dropping other groups. |
| The discovery POD example reused a subscription ID. A late EOSE could complete a later lookup. | Use a fresh ID for each lookup and execute the actual POD text through Client message handlers, including a stale EOSE. Document production transport completeness, timeout cleanup, and pagination responsibilities. |
| The metadata-edit POD example enabled both sides of every opposing flag pair. | Replace it with a consistent example and execute the actual POD text. Metadata, pins, and PaymentTargets examples are also extracted from POD and run. |

Additional coverage now explicitly exercises opt-in group policy, default and
reversed access flags, preservation of omitted flags, public history/metadata
reads, ordinary-kind restrictions including an empty list, cross-group and
non-admin deletion rejection, successful deletion, unsupported moderation/AV
actions, own-author timeline references, future timestamps, missing group
tags, duplicate payment targets, and overlapping-filter completeness hints.

## Scope and limits

This reviews the September changes and their interactions, not every previously
released constructor/parser or every requirement in all advertised NIPs. It
does not establish exhaustive coverage of every possible input or schedule.
The generic NIP-51 list helper still leaves kind-specific item semantics to
applications; the NIP-46 payload helper is not a signer dispatcher.

External discovery services, live relay interoperability, Windows, persistent
store failures/transactions, and restart recovery with a third-party backend
were not exercised. Discovery transport and persistence are application-owned.
Generated membership timestamps can advance beyond wall-clock time during
rapid transitions; downstream clients must not assume they equal receipt time.
The default bounded in-memory store can evict group state or history and is
unsuitable for durable groups without an appropriate persistent backend.
LiveKit services, group replicas/history import, and network-specific payment
address checks remain outside the implemented helpers.
